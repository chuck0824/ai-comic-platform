# 统一任务事件中心完善设计

日期：2026-07-04

状态：待用户审阅

范围：用户任务中心、运营任务控制台、生成任务、剧本交易任务、积分/钱包流水、告警、SLA、自动对账与人工处置

## 1. 结论

新增独立“任务中心”，采用统一任务事件中心架构，同时覆盖生成任务与剧本交易任务。中心不接管各业务域的状态机，而是通过标准事件、追加时间线和可重建读模型，提供统一查询、权限化操作入口、SLA、告警、对账、补偿与工单能力。

产品提供两套视图：

- 用户任务中心：当前 Workspace 内的生成、交易、费用和待办；
- 运营任务控制台：跨 Workspace 的全局态势、异常队列、对账、告警、补偿与工单。

首个可用版本同时包含操作闭环和基础治理，不先交付一次性只读页面。后续迭代增强告警降噪、规则编排、自动恢复率和规模化存储。

本设计覆盖 `2026-07-04-asset-generation-history-workbench-design.md` 中“删除独立任务监控入口”的决定。资产工作台继续负责成功资产的整理、复用、发布和回收；任务中心独立负责执行过程、费用、交易和异常。两者通过 `task_uuid`、`asset_uuid` 和关联项目互相跳转。

## 2. 现状与缺口

### 2.1 前端问题

现有 `TaskMonitor.vue` 不是完整监控模块：

1. 列表读取 `scriptApi.getTaskHistory()`，数据源是脚本域 `gen_tasks`；取消和重试却调用生成域 `/generation/tasks/{uuid}`，作用于 `generation_tasks`，读写对象不一致。
2. 只加载前 20 条并在前端统计，没有服务端分页、Workspace 范围、复合筛选、错误态、空态和请求竞态保护。
3. 状态同时使用 `running/processing`、`succeeded/completed` 等口径，进度、颜色和可用操作并不可靠。
4. 页面没有任务详情、阶段时间线、执行尝试、输入输出、关联项目/资产、错误诊断、费用构成和积分流水。
5. 用户无法继续支付、查看交付、提交退款或补充凭证；运营无法查单、重发交付、发起补偿、认领异常或关联工单。
6. 每 10 秒整页轮询，缺少增量推送、断线续传和事件游标。

### 2.2 生成任务问题

1. `GenerationController` 只有单任务查询，没有统一列表、facets、时间线或批量查询。
2. `GenerationService.createTask()` 没有从安全上下文写入 Workspace、创建人、请求 ID 和幂等键；数据库默认值可能造成错误归属。
3. 取消只允许 `pending`，没有供应商取消、运行中协作取消、冻结积分释放和取消结果确认。
4. 重试没有完整复制 Workspace 上下文，也没有写入 `retry_of_task_id`，无法形成可靠重试链。
5. 费用仅按任务类型返回固定估算值；`CreditTransactionMapper` 未形成预估、冻结、实扣、补扣、释放和退款闭环。
6. `GenerationExecutor` 在 AI Router 将任务标记为成功后才回写节点和登记资产；资产登记异常被吞掉，可能出现“任务成功但没有有效资产”。
7. 异步所有者解析失败会回退到用户 `1`，存在 Workspace 隔离和资产归属风险。
8. 已有 `generation_settlement_outbox` 表和实体，但尚未形成完整投递、重试、死信、告警和对账闭环。

### 2.3 交易与财务监控问题

交易域已经具备订单、支付、权益、交付、退款和 Outbox 基础，但当前任务监控没有接入：

- 个人订单与企业采购审批；
- 支付处理与 3001 钱包转账；
- 权益快照和已购副本交付；
- 卖家冻结期与结算释放；
- 退款审核、原交易冲正和授权恢复；
- 支付成功未交付、订单与账本不一致、冲正失败等异常。

结果是用户无法在一个入口理解“钱到了哪一步”，运营也缺少统一异常发现和处置队列。

## 3. 已确认的产品决策

1. 采用独立“任务中心”，不合并到资产工作台。
2. 同时覆盖生成任务、交易任务和对应积分/钱包流水。
3. 提供用户视图和运营视图，复用同一事件模型，使用不同权限和信息密度。
4. 采用统一任务事件中心；各业务服务继续拥有自己的事实数据和状态迁移权。
5. 首期融合可操作闭环与治理：取消、重试、支付、交付重试、退款、补偿、基础告警、SLA、自动查单和人工工单共同交付。
6. 不允许任务中心直接修改业务状态或余额；命令必须回源业务服务执行。

## 4. 目标与非目标

### 4.1 目标

- 用一个入口解释生成与交易从创建到终态的全过程。
- 明确区分业务失败、系统异常、SLA 超时和账实不一致。
- 打通生成任务的积分预估、冻结、结算、释放和退款。
- 打通交易订单的审批、支付、交付、卖家结算、退款和冲正。
- 为用户提供安全可用的自助操作，为运营提供异常治理闭环。
- 保证事件重放、重复投递和命令重试不会造成重复扣费、重复交付或重复退款。
- 保证 Workspace 隔离、敏感信息脱敏、危险财务操作审批和完整审计。

### 4.2 非目标

本期不建设通用 BPM/工作流编排平台，不把生成、订单和钱包状态机迁入任务中心；不替代 3001 钱包账本；不在任务中心管理资产元数据和市场发布；不直接实现客服 IM、复杂排班或机器学习异常预测。

## 5. 总体架构

```text
生成域                 交易域                    3001 钱包域
generation_tasks       orders/refunds/delivery   ledger/transfers/reversals
        │                       │                         │
        └──────────── 领域事件 / Outbox / 查单兜底 ───────┘
                                │
                  ┌─────────────▼─────────────┐
                  │    统一任务事件中心        │
                  │  事件库 / 投影 / 关联图     │
                  │  操作路由 / SLA / 对账      │
                  │  告警 / 补偿 / 工单 / 审计  │
                  └──────────┬───────┬────────┘
                             │       │
                    用户任务中心   运营任务控制台
```

### 5.1 组件职责

| 组件 | 职责 |
|---|---|
| Domain Event Adapters | 将生成、交易和钱包事件转换为统一事件信封；保留原域 payload 引用 |
| Task Event Store | 追加保存脱敏事件；以来源和事件 ID 幂等 |
| Task Projector | 生成 Task Case 摘要、阶段、健康度、时间线、关联对象和允许操作 |
| Command Router | 鉴权、幂等、审批校验并把命令路由回所属业务服务 |
| SLA & Alert Engine | 计算阶段截止时间，产生、聚合、关闭和升级告警 |
| Reconciliation Engine | 比较生成/订单事实、Outbox 和 3001 账本，自动查单和生成差异案件 |
| Work Order Adapter | 对无法自动恢复的异常创建、认领、转派和关闭工单 |
| User Task Center | 当前 Workspace 的任务、交易、费用和待办 |
| Ops Task Console | 全局态势、异常队列、对账、告警、补偿和审计 |

### 5.2 边界规则

- 生成、交易、钱包仍是各自事实源；任务中心的查询投影允许重建。
- 取消、重试、支付、退款和补偿必须通过 Command Router 回源，禁止直接更新业务表。
- 任务中心不保存或计算可花费余额；余额和不可变账本只由 3001 提供。
- 资产工作台展示成功资产，任务中心展示任务过程；任务成功资产可相互跳转。

## 6. 统一 Task Case 模型

Task Case 是跨服务可观察与处置的聚合，不是新的业务订单。一个 Task Case 可以关联一个主业务对象和多个执行尝试、财务交易、资产、退款或工单。

### 6.1 顶层状态

`summary_status` 使用：

- `WAITING_ACTION`：等待用户、审批人或运营操作；
- `IN_PROGRESS`：系统正在排队、执行、支付、交付、结算或自动恢复；
- `SUCCEEDED`：该 Case 的成功条件全部满足；
- `FAILED`：业务已终止且补偿完成，不需要继续系统处置；
- `CANCELED`：已按规则取消且相关资金处理完成；
- `EXCEPTION`：存在系统异常、账实不一致或补偿未完成。

`health_status` 独立使用：`NORMAL`、`AT_RISK`、`SLA_BREACHED`、`INCONSISTENT`。顶层状态与健康度不可互相替代。例如支付成功但交付失败是 `IN_PROGRESS + INCONSISTENT` 或 `EXCEPTION + INCONSISTENT`，不是“支付失败”。

### 6.2 通用字段

- 身份：`case_uuid`、`domain`、`task_type`、Workspace、创建人、责任方；
- 状态：`summary_status`、`domain_stage`、`health_status`、进度、下一动作；
- 时间：创建、开始、最近事件、阶段截止和完成时间；
- 财务投影：预估、冻结、实扣、退款/冲正及账本交易引用；
- 关联：内容项目、画布、节点、生成任务、订单、退款、权益、资产和工单；
- 追踪：`request_id`、`trace_id`、`idempotency_key`、聚合版本和重试链。

### 6.3 重试语义

用户或运营重试会创建新的 `task_attempt`，不能覆盖原尝试。新尝试记录自己的供应商请求 ID、开始/结束时间、错误、输入快照摘要和费用。Case 的汇总状态由所有尝试和当前业务事实计算。

## 7. 生成任务流程

标准生成流程：

```text
创建
→ 参数与权限校验
→ 积分预估
→ 冻结/预扣
→ 排队
→ 模型执行
→ 输出文件校验
→ 资产与版本入库
→ 节点/分镜回写
→ 实际费用结算
→ SUCCEEDED
```

### 7.1 成功条件

生成任务只有在以下条件全部满足后才能成功：

1. 模型调用产生有效输出；
2. 文件可访问且基础元数据校验通过；
3. 至少一个有效 `asset_version` 已登记；
4. 必要的节点或分镜回写完成；
5. 实际费用已结算或收到可确认的账本回执。

资产登记或结算失败时任务进入 `EXCEPTION` 并创建补偿事件，不允许提前标记成功。

### 7.2 取消与失败

- 排队中取消：取消队列项并释放冻结积分；
- 运行中取消：先请求供应商取消；若供应商不能取消，展示“取消处理中”，最终按实际消耗结算；
- 执行失败：记录标准错误码，释放未消费冻结额，必要时退款；
- 结算失败：保留模型输出和资产，进入财务异常队列，禁止重复生成来规避对账；
- 重试：创建新尝试，重新估价和冻结，不复用已结算费用。

## 8. 交易任务流程

### 8.1 个人购买

```text
创建订单
→ 待支付
→ 支付处理中
→ 支付成功
→ 权益快照
→ 已购副本交付
→ 卖家资金冻结期
→ 卖家结算释放
→ SUCCEEDED
```

支付成功但交付失败时，订单保持已支付事实，Task Case 进入交付异常。系统优先幂等重发交付，不允许用户重复付款。

### 8.2 企业采购

企业流程在支付前增加 `PENDING_APPROVAL`。批准、驳回、撤回、过期均形成事件。批准后进入正常支付与交付流程；审批权限和支付权限分别校验。

### 8.3 退款与冲正

```text
退款申请
→ 资料补充/审核
→ 批准或驳回
→ 按原交易冲正
→ 权益回收或状态调整
→ 独家/买断库存恢复
→ REFUNDED / CLOSED
```

冲正不得超过原交易可退余额。权益和库存只在冲正确认后恢复。冲正失败进入 `EXCEPTION + INCONSISTENT`，由自动查单和人工工单处理。

## 9. 页面设计

### 9.1 用户任务中心 `/task-center`

导航页签：概览、生成任务、交易订单、费用明细。

概览展示进行中、待我处理、本月费用和异常数量。列表支持关键词、状态、类型、项目、模型/支付渠道和时间筛选，并区分无数据、无匹配、无权限与加载失败。

用户可执行：

- 生成：取消、重试、复制参数、查看或跳转资产；
- 交易：继续支付、取消未支付订单、查看交付、申请退款、补充凭证；
- 通用：查看时间线、费用、关联对象、帮助说明和联系支持。

### 9.2 运营任务控制台 `/ops/task-center`

导航页签：全局态势、生成、交易、对账异常、告警、工单。

运营可按 Workspace、用户、`trace_id`、订单号、任务号、模型、供应商、支付渠道、错误码、严重度、责任域和 SLA 状态筛选。

运营可执行：认领、转派、重新查单、重发交付、重跑资产入库、发起补偿、关闭/静默告警和关联工单。所有动作由后端 `allowed_actions` 决定。

### 9.3 详情抽屉

详情统一包含：

1. 概览与下一动作；
2. 业务阶段和事件时间线；
3. 费用、账本引用与对账状态；
4. 输入输出摘要和关联资产；
5. 执行尝试与错误诊断；
6. 告警、补偿和工单；
7. 审计记录。

Prompt、合同、支付凭证、个人信息和账本明细按权限脱敏。

### 9.4 实时更新

页面优先使用 SSE 获取增量事件，使用游标断线续传。SSE 不可用时回退到带 ETag/更新时间的增量轮询，不再每 10 秒重载整页。

## 10. 数据模型

### 10.1 `task_cases`

保存统一查询摘要：`case_uuid`、`workspace_id`、`domain`、`task_type`、`summary_status`、`domain_stage`、`health_status`、`progress`、`created_by`、`current_owner`、`next_action`、`sla_due_at`、`last_event_at`、财务摘要、聚合版本和审计时间。

建议索引：

- `(workspace_id, summary_status, last_event_at DESC)`；
- `(workspace_id, domain, task_type, created_at DESC)`；
- `(health_status, sla_due_at)`；
- `(current_owner, summary_status, last_event_at DESC)`。

### 10.2 `task_case_links`

字段：`case_id`、`link_type`、`source_system`、`external_id`、`display_ref`、`created_at`。`link_type` 支持 generation_task、order、refund、wallet_transfer、entitlement、asset、content_project、canvas_project、node 和 work_order。唯一约束为 `(case_id, link_type, source_system, external_id)`。

### 10.3 `task_events`

字段：`case_id`、`source_system`、`event_id`、`event_type`、`aggregate_type`、`aggregate_id`、`aggregate_version`、`occurred_at`、`received_at`、`actor_type`、`actor_id`、`payload`、`trace_id`。

唯一约束 `(source_system, event_id)`。事件追加后不可修改；需要纠正时追加补正事件。payload 只保存脱敏摘要和必要快照，大对象使用引用。

### 10.4 `task_attempts`

记录 `case_id`、`attempt_no`、`source_task_id`、`provider_request_id`、`status`、`started_at`、`completed_at`、`error_code`、`error_summary`、估算/实际费用和 `retry_of_attempt_id`。

### 10.5 `task_alerts`

记录规则、严重度、首次/最近触发时间、聚合键、状态、负责人、静默截止、升级级别和关闭原因。状态为 OPEN、ACKNOWLEDGED、RESOLVED、SUPPRESSED。

### 10.6 `reconciliation_cases`

记录对账类型、左右事实引用、差异金额/状态、自动处理次数、当前结论、责任域、工单和解决时间。财务金额使用最小货币单位或整数积分，不使用浮点数。

### 10.7 `task_commands`

记录 `idempotency_key`、`request_hash`、Case、action、操作者、操作原因、审批状态、目标服务、响应摘要和审计时间。同一 Workspace、操作者、幂等键的重复请求必须返回原结果；相同幂等键但请求哈希不同必须拒绝。

## 11. 事件契约与投影

统一事件信封至少包含：

```json
{
  "event_id": "uuid",
  "event_type": "trade.delivery.failed",
  "source_system": "aicp-trade",
  "aggregate_type": "trade_order",
  "aggregate_id": "order_no",
  "aggregate_version": 7,
  "workspace_id": "personal_123",
  "occurred_at": "2026-07-04T10:00:00+08:00",
  "trace_id": "trace_uuid",
  "payload": {}
}
```

事件采用至少一次投递：

- 重复事件由唯一键忽略；
- 同一聚合的旧版本不得覆盖新投影；
- 版本存在缺口时暂存并触发回源查询；
- 无版本事件按发生时间投影，但财务终态必须回源确认；
- 连续失败进入死信队列并产生告警；
- 支持按 Case、Workspace 和时间段重放投影。

## 12. API 契约

### 12.1 用户查询

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/v1/task-center/overview` | 用户任务概览 |
| GET | `/api/v1/task-center/cases` | 分页列表与筛选 |
| GET | `/api/v1/task-center/cases/{caseUuid}` | Case 详情与 `allowed_actions` |
| GET | `/api/v1/task-center/cases/{caseUuid}/events` | 游标分页时间线 |
| GET | `/api/v1/task-center/facets` | 状态、类型、项目、模型和渠道计数 |
| GET | `/api/v1/task-center/stream` | SSE 增量事件，支持 cursor |

### 12.2 命令

统一使用：

`POST /api/v1/task-center/cases/{caseUuid}/commands/{action}`

请求必须携带 `Idempotency-Key`，危险操作要求 `reason`。可用 action 包括 cancel、retry、continue_payment、cancel_order、submit_refund、add_evidence、claim、assign、requery_payment、redeliver、retry_asset_registration、request_compensation、ack_alert 和 close_alert。

Command Router 根据 Case 域、当前事实、权限和审批状态路由到原业务服务。命令接受不表示业务完成；响应返回命令状态，最终结果由事件更新。

### 12.3 运营查询

| 方法 | 路径 | 用途 |
|---|---|---|

## 13. SLA、告警、对账与工单

### 13.1 首批规则

- 生成排队超过任务类型阈值；
- 模型执行超过供应商/模型阈值；
- 模型成功后 2 分钟无有效资产；
- 生成终态后 5 分钟无结算回执；
- 支付成功后 2 分钟未创建权益；
- 权益创建后 2 分钟未完成交付；
- 退款批准后 10 分钟未完成原交易冲正；
- 订单、Outbox 和 3001 账本状态或金额不一致。

具体阈值由配置表按任务类型、模型、渠道和业务阶段覆盖，以上为初始默认值。

### 13.2 严重度

- P1：资金重复扣除、批量支付/交付异常、账本不可用或大面积任务阻塞；
- P2：单笔财务不一致、补偿耗尽、关键交付失败；
- P3：单任务超时、可自动恢复的供应商错误；
- P4：信息缺失、非阻断性数据质量问题。

### 13.3 自动处置

系统先执行无副作用查单，再执行幂等补偿。每条规则设置最大尝试数、指数退避和总时限。超过阈值时生成工单并通知责任人，不允许无限重试。

### 13.4 财务安全

人工冲正、退款、赠送积分等操作必须二次确认；超过配置金额或积分阈值必须双人审批。所有财务修复都通过 3001 的原交易冲正或正式账本接口完成，禁止直接修改余额。

## 14. 权限、安全与审计

- 用户查询强制 `X-Workspace-Id` 与成员权限；不得依赖前端传入 user ID。
- 普通用户只看当前 Workspace 中有权访问的 Case；企业审批人额外看到待其审批的采购任务。
- 运营跨 Workspace 查询需要独立权限，并记录查询理由、操作者和条件摘要。
- `allowed_actions` 由后端结合角色、事实状态、审批和风险阈值返回。
- Prompt、密钥、支付凭证、合同正文、个人信息和完整账本不进入普通事件 payload。
- 所有命令、审批、补偿、静默告警、导出和敏感查看都写入不可变审计日志。

## 15. 错误处理

- API 使用稳定错误码，区分权限、状态冲突、余额不足、幂等冲突、供应商失败、账本不可用和补偿处理中。
- 用户端展示可行动文案，不暴露内部堆栈、渠道密钥或供应商原始敏感响应。
- 运营端显示标准错误码、责任域、最近尝试和推荐动作，可按权限查看脱敏原始引用。
- 操作超时后客户端不得假定失败；必须使用命令 ID 查状态，避免重复支付或补偿。
- SSE 断线不改变业务状态；客户端使用 cursor 补拉缺失事件。

## 16. 迁移与兼容

1. 建立统一表、事件适配器和影子投影，不切换现有页面。
2. 回填最近 90 天活跃任务、全部未终结生成任务、未终结订单、退款和异常 Outbox；更早历史按需加载。
3. 将 `gen_tasks` 映射到统一 Case，仅用于历史兼容；所有新生成任务统一写入 `generation_tasks`。
4. 双读比对状态、数量、Workspace、费用和终态；差异生成迁移报告，不在查询时静默修复。
5. 灰度切换 `/task-monitor` 到 `/task-center`，保留路由重定向和回滚开关。
6. 资产工作台删除任务列表职责，但保留从资产查看来源任务、从任务跳转结果资产。
7. 稳定期结束后停止 `gen_tasks` 作为监控数据源，保留旧 ID 到 Case 的映射。

迁移期间不得把无法确定 Workspace 或创建人的记录回退到固定用户。无法可靠归属的数据进入隔离队列，仅运营可见。

## 17. 测试策略

### 17.1 单元与状态机测试

- 生成正常、取消、供应商超时、失败重试、资产入库失败、结算失败；
- 个人购买、企业审批、支付失败、支付成功未交付、卖家结算、退款与冲正；
- 顶层状态、健康度、下一动作和 `allowed_actions` 投影。

### 17.2 事件可靠性测试

- 重复、乱序、延迟、版本缺口、死信和事件重放；
- 消费者重启、Outbox 重投和网络超时；
- 任何场景不得重复扣费、交付、退款或创建资产。

### 17.3 权限与安全测试

- 跨 Workspace 读取和命令越权；
- 运营权限、审批绕过、金额阈值和审计完整性；
- 事件 payload、日志、导出和错误文案的敏感数据泄漏。

### 17.4 端到端测试

- 生成：预估 → 冻结 → 执行 → 资产 → 结算 → 页面实时更新；
- 交易：下单 → 支付 → 权益 → 交付 → 卖家结算；
- 异常：支付成功未交付 → 告警 → 自动重发 → 恢复；
- 对账：账本回执丢失 → 差异 Case → 查单 → 补正投影；
- 人工：异常认领 → 补偿审批 → 执行 → 审计 → 工单关闭。

### 17.5 性能与恢复测试

- 列表高基数筛选、时间线游标分页和运营聚合；
- SSE 大量连接、断线续传和降级轮询；
- 投影全量/局部重建和数据库故障恢复。

## 18. 发布分期

### R1：统一底座与可操作闭环

- 统一事件契约、Task Case、时间线、执行尝试和关联模型；
- 生成与交易事件适配；
- 用户任务中心和基础运营异常队列；
- 取消、重试、支付、退款申请、重发交付和重跑资产登记；
- 生成积分冻结/结算/退款；
- 首批 SLA、告警和自动查单规则。

### R2：运营治理与自动对账

- 运营全局态势、认领/转派、工单；
- 生成、交易和 3001 三方自动对账；
- 财务补偿审批和完整审计；
- 可配置 SLA、告警升级和通知。

### R3：规模化与智能治理

- 告警聚合降噪、维护窗口和供应商故障归因；
- 成本异常、容量和恢复率报表；
- 事件冷热分层、归档和大规模投影重建。

## 19. 验收指标

- 列表查询 P95 不超过 300ms；
- 事件产生到页面可见 P95 不超过 5 秒；
- SSE 断线后可按 cursor 补齐事件；
- 重复/重放场景下重复扣费、重复交付、重复退款为 0；
- 100% 用户和运营命令具备操作者、原因、幂等键和结果审计；
- 100% 财务差异可追溯到原订单/任务和原账本交易；
- 已定义异常规则的自动发现率不低于 99%；
- 补偿命令幂等率 100%；
- Workspace 越权和审批绕过测试全部拒绝；
- R1 上线前，现有 `gen_tasks` 与 `generation_tasks` 双口径问题必须消除。

## 20. 方案自检结论

- 范围已限定为生成、剧本交易及其财务治理，没有扩展为通用工作流平台。
- Task Case、业务事实源和钱包账本职责不重叠。
- 用户端与运营端的权限、信息密度和危险操作边界明确。
- 成功、失败、异常、SLA 超时和账实不一致的语义互不冲突。
- R1 已包含基础治理能力，与“B 与 C 融合”的决策一致。
- 迁移明确处理两套任务表和旧资产工作台方案冲突。

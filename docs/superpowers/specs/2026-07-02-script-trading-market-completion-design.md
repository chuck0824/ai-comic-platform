# 剧本交易市场完善设计

> 日期：2026-07-02  
> 状态：已确认  
> 范围：剧本市场、上架审核、个人/企业采购、统一钱包、授权交付、卖家结算与受控退款

## 1. 背景与现状

当前剧本交易市场尚未形成真实交易能力：

- `aicp-frontend/src/views/Market.vue` 使用硬编码卡片，筛选只作用于本地数组，“查看详情”没有实际路由。
- `aicp-frontend/src/api/trade.js` 已声明部分市场、订单、企业采购、销售和提现接口，但没有被完整页面流程使用。
- `TradeController` 直接返回固定市场、订单、支付和收益数据，没有调用 `TradeService`。
- `TradeService` 仍使用固定买家 ID、客户端金额和卖家 ID，无法作为可信交易实现。
- 现有 `orders`、`script_listings` 等表不足以表达价格快照、授权库存、交付、退款、资金账本和跨服务补偿。
- 3001 已具备账户、充值渠道、充值回调、用户额度和订阅支付能力，但没有通用剧本订单钱包接口。现有充值接口不能直接充当商品订单支付接口。

本设计以“8080 管交易业务、3001 管统一资金钱包”为边界，完成免费领取、普通授权、独家授权和买断授权的完整闭环。

## 2. 目标

1. 建立“上架—审核—发现—试读—下单—支付—授权—入库—结算—售后”的完整流程。
2. 个人和企业采购统一使用 3001 钱包；8080 只提供充值入口和交易编排，不建立第二套钱包。
3. 支持免费、普通、独家和买断四种授权，并保证独家/买断并发库存正确。
4. 支持企业 Workspace 采购申请、审批、付款和企业仓库授权。
5. 使用账本、幂等键、Outbox 和补偿任务保证跨服务交易可恢复、可对账、可审计。
6. 支持卖家冻结收入、7 天结算、退款申诉和原交易冲正。

## 3. 非目标

- 本期不实现法务电子签章、司法存证或版权登记代办。
- 本期不实现跨币种交易、汇率换算和国际税务计算。
- 本期不实现优惠券、满减、竞价、拍卖、订阅制剧本包或多商品购物车。
- 本期不实现自动银行卡/第三方支付渠道分账；卖家收入进入统一 3001 钱包。
- 本期不重构与交易闭环无关的生成、画布和资产市场模块。

## 4. 核心原则

### 4.1 单一职责

- 8080 是剧本交易业务真相：上架、价格与协议快照、订单、授权、交付、退款业务状态。
- 3001 是资金真相：个人/企业钱包、充值、冻结、转账、解冻、冲正和资金流水。
- 前端不直接拼装可信价格、卖家、平台费或钱包账户。

### 4.2 账本优先

3001 现有 `quota` 字段保留为兼容投影。钱包余额必须由不可变账本流水汇总或可靠投影得出，任何剧本交易都不得直接加减单一余额字段。

### 4.3 快照交付

价格、协议和剧本版本都在下单时冻结。买家获得的是购买时的剧本快照和授权凭证；卖家后续编辑不会静默修改已购内容。

### 4.4 可恢复一致性

8080 与 3001 不共享数据库，也不使用分布式数据库事务。通过幂等接口、状态机、Outbox、主动查单和补偿任务实现最终一致性。

## 5. 系统边界

### 5.1 8080 职责

- 市场搜索、详情、试读和收藏。
- 剧本上架申请、内容审核、定价、授权库存和下架。
- 个人订单和企业采购申请。
- 订单状态机、授权凭证、仓库副本和使用限制。
- 退款申请、平台审核及退款业务状态。
- 卖家销售数据、交易通知和完整审计记录。
- 调用 3001 钱包接口并处理跨服务补偿。

### 5.2 3001 职责

- 个人钱包和企业 Workspace 钱包。
- 充值商品、支付渠道、渠道回调和充值入账。
- 余额查询、预检查、原子扣款、平台费、卖家冻结入账。
- 冻结收入解冻、退款冲正和资金流水查询。
- 钱包接口鉴权、服务签名、幂等和资金对账。

### 5.3 调用关系

```text
浏览器
  ├─ 市场/订单/授权/退款 ─────────────→ 8080
  └─ 充值支付页（由 8080 提供入口） ───→ 3001 支付能力

8080 ──服务签名 + 业务订单号 + 幂等键──→ 3001 钱包内部接口
3001 ──可信结果通知 / 8080 主动查单────→ 8080 订单编排
```

## 6. 用户与业务流程

### 6.1 卖家上架

1. 卖家从自己的 Workspace 仓库选择一个可交易剧本版本。
2. 填写封面、简介、试读集数、四轴标签和授权方案。
3. 每个授权方案保存价格、期限、账号上限、商业使用、改编权和转授权限制。
4. 提交后形成不可变审核版本，状态进入 `UNDER_REVIEW`。
5. 平台审核通过后状态变为 `LISTED`；驳回时必须返回原因。
6. 卖家修改剧本内容、授权协议或关键定价信息后必须重新审核。
7. 下架只阻止新订单，不影响既有订单、授权和已购副本。

### 6.2 个人购买

1. 买家浏览市场、查看详情并试读允许公开的剧集。
2. 选择购买主体为个人 Workspace，并选择授权类型。
3. 8080 从上架快照计算金额并创建订单；客户端金额仅用于一致性提示。
4. 普通/免费授权直接进入待支付；独家/买断同时建立 30 分钟库存保留。
5. 免费订单执行零金额钱包凭证后直接交付；非免费订单调用 3001 钱包。
6. 余额不足时进入 8080 充值入口，由 3001 返回可用渠道并完成充值。
7. 充值成功返回原订单，用户明确点击“确认支付”。
8. 3001 原子完成买家扣款、平台收入、卖家冻结收入。
9. 8080 生成授权凭证及买方仓库副本，将订单置为 `FULFILLED`。
10. 页面提供“进入仓库”和“使用此剧本开始制作”两个后续入口。

### 6.3 企业采购

1. 企业成员选择目标企业 Workspace、授权方案并填写采购理由。
2. 8080 校验成员身份和 `trade.purchase.request` 权限，创建 `PENDING_APPROVAL` 采购申请。
3. 审批人查看预算、Workspace 钱包余额、授权条款和历史授权披露。
4. 审批人使用 `trade.purchase.approve` 权限批准或驳回。
5. 审批通过后才创建/激活支付订单并开始独家或买断库存保留。
6. 申请人或有付款权限的成员明确确认付款，不允许“审批即静默扣款”。
7. 3001 只从目标 Workspace 钱包扣款，禁止个人钱包代扣企业订单。
8. 授权凭证和剧本副本进入企业 Workspace 仓库。

### 6.4 卖家结算

1. 支付成功时，卖家收入进入 3001 钱包的冻结余额。
2. 平台费立即进入平台钱包，但必须与原交易关联，可被退款冲正。
3. 订单完成后进入 7 天结算期。
4. 无退款处理中的订单到期后由 8080 触发 3001 解冻。
5. 解冻具有稳定幂等键；任务重试不得重复增加可用余额。
6. 卖家中心分别展示待结算、可用、累计收入及退款冲减。

### 6.5 售后与退款

- 未支付订单可主动取消，或 30 分钟后自动过期。
- 已支付但未完成授权入库的订单由系统自动全额退款。
- 已完成交付的数字内容不支持买家自行即时退款，只能提交平台申诉。
- 平台审核退款时保存原因、证据、审核人和审核时间。
- 退款必须由 3001 对原钱包转账执行冲正，不允许直接修改余额。
- 退款处理中，独家/买断授权库存保持锁定。
- 独家/买断退款完成后撤销对应授权和买方可用权限，再恢复上架库存；仓库保留不可使用的审计副本，不物理删除。

## 7. 授权模型

### 7.1 授权类型

| 类型 | 库存 | 金额 | 交付结果 |
|---|---:|---:|---|
| `FREE` | 可重复 | 0 | 授权凭证 + 仓库快照 |
| `NORMAL` | 可重复 | 大于等于 0 | 有限商业授权 + 仓库快照 |
| `EXCLUSIVE` | 1 | 大于 0 | 独家使用授权 + 仓库快照 |
| `BUYOUT` | 1 | 大于 0 | 合同约定财产权利转让 + 仓库快照 |

### 7.2 排他规则

- 独家和买断共享一个排他库存，只能有一笔最终成交。
- 独家或买断支付完成后，Listing 立即停止所有新授权销售。
- 成交前已经完成的普通授权继续有效。
- 详情页和订单确认页必须展示历史有效普通授权数量。
- 创建独家/买断订单时使用数据库条件更新或唯一保留记录锁定库存；不得仅在应用内先查后写。
- 买断不删除作者署名、订单、历史授权和审计记录。

### 7.3 授权条款快照

每个订单项保存：

- 授权类型、授权主体和授权剧本版本。
- 价格、币种、期限和生效时间。
- 允许发布的账号数量和平台范围。
- 商业使用、改编、转授权、二次销售和地域限制。
- 历史普通授权数量披露。
- 协议文本版本、摘要和内容哈希。

## 8. 状态机

### 8.1 Listing 状态

```text
DRAFT → UNDER_REVIEW → LISTED → UNLISTED
             └──────→ REJECTED → DRAFT
LISTED → EXCLUSIVE_RESERVED → LISTED（保留过期/支付失败）
LISTED/EXCLUSIVE_RESERVED → EXCLUSIVE_SOLD
```

`EXCLUSIVE_SOLD` 同时覆盖独家和买断最终成交，具体类型由授权凭证记录。

### 8.2 订单状态

```text
PENDING_APPROVAL → PENDING_PAYMENT → PAYING → PAID_PENDING_DELIVERY → FULFILLED
        │                 │             │                │
        └→ REJECTED       ├→ CANCELLED  ├→ PAYMENT_FAILED├→ COMPENSATING
                          └→ EXPIRED     └→ PAYMENT_UNKNOWN└→ REFUNDED

FULFILLED → REFUND_REQUESTED → REFUND_PROCESSING → REFUNDED
                            └────────────→ REFUND_REJECTED → FULFILLED
```

### 8.3 钱包转账状态

```text
CREATED → PROCESSING → SUCCEEDED
                  ├──→ FAILED
                  └──→ UNKNOWN → SUCCEEDED / FAILED
SUCCEEDED → PARTIALLY_REVERSED / REVERSED
```

未知状态禁止再次使用新幂等键扣款；必须使用原业务订单号查单。

## 9. 8080 数据模型

### 9.1 `script_listings`

保存 `workspace_id`、`seller_user_id`、`script_id`、`script_version_id`、公共信息快照、试读范围、审核状态、上架状态、历史普通授权数、排他库存状态、保留订单与过期时间、行版本和时间戳。

公开市场只读取 `LISTED` 或可展示的 `EXCLUSIVE_RESERVED` 快照，不直接跨 Workspace 读取卖家私有剧本。

### 9.2 `listing_license_options`

保存 Listing 下的授权类型、价格（分）、币种、授权条款 JSON、协议文本版本、内容哈希、启用状态和行版本。`EXCLUSIVE` 与 `BUYOUT` 不得同时存在有效成交。

### 9.3 `trade_orders`

保存：

- 订单号和状态。
- 买方用户、买方 Workspace 及类型。
- 卖方用户和卖方 Workspace。
- 总金额、平台费、卖家收入、币种。
- 3001 钱包转账号和最后一次已知资金状态。
- 过期、支付、交付、完成和退款时间。
- 幂等创建键、行版本和异常原因。

金额字段统一使用 `BIGINT` 最小货币单位，人民币使用分，Java 使用 `long` 或精确整数类型，禁止浮点数。

### 9.4 `trade_order_items`

一期每单一个剧本，但仍使用订单项固定快照边界。保存 Listing、剧本版本、授权类型、价格、公共信息、授权条款和协议哈希。

### 9.5 `script_entitlements`

保存受益 Workspace、订单项、剧本版本、授权类型、状态、授权范围、生效/失效时间和撤销原因。唯一约束保证一个订单项只能生成一份有效授权。

### 9.6 `purchased_script_copies`

保存买方 Workspace 下的仓库副本、来源订单、来源剧本版本、内容快照、只读来源元数据和可用状态。买家后续可以在自己的项目中派生可编辑副本，但不修改来源快照。

### 9.7 `purchase_requests`

保存企业 Workspace、申请人、审批人、Listing、授权方案、金额快照、理由、状态、审批意见和时间。审批通过不自动扣款。

### 9.8 `refund_requests`

保存订单、申请人、原因代码、说明、证据、状态、审核人、审核意见、退款金额、3001 冲正号和时间。

### 9.9 `trade_outbox_events`

保存聚合类型、聚合 ID、事件类型、载荷、状态、重试次数、下次重试时间和最后错误。业务状态变更和 Outbox 写入必须处于同一 8080 数据库事务。

### 9.10 `trade_audit_logs`

保存操作者、Workspace、动作、对象、前后状态摘要、请求关联 ID、客户端信息和时间。资金敏感字段只保存脱敏引用，不保存支付密钥。

## 10. 3001 钱包模型

### 10.1 `wallet_accounts`

- 所有者类型：`USER`、`WORKSPACE`、`PLATFORM`。
- 所有者 ID、币种、可用余额、冻结余额、状态和行版本。
- 同一所有者与币种只能有一个有效钱包。

### 10.2 `wallet_transfers`

保存外部业务类型、外部业务订单号、幂等键、转账类型、金额、状态、冲正来源、请求哈希和时间。业务订单号与转账类型建立唯一约束。

### 10.3 `wallet_ledger_entries`

采用不可变复式账本。一次购买至少包含：

- 买方可用余额减少。
- 卖方冻结余额增加。
- 平台费收入增加。
- 必要的清算中间账户分录。

借贷合计必须平衡。流水创建后不得更新金额或删除，只能通过新冲正流水抵消。

### 10.4 `wallet_idempotency_records`

保存调用方、幂等键、请求哈希、处理状态和响应快照。同一个幂等键携带不同金额或账户时返回冲突，不能沿用首次结果。

### 11.5 3001 用户侧充值 API

8080 充值页复用 3001 已有能力：

- `GET /api/user/topup/info`
- `GET /api/user/topup/self`
- `POST /api/user/pay`（易支付）
- `POST /api/user/stripe/pay`
- 其他已配置支付渠道

充值仍由 3001 创建充值单、处理渠道回调并记入用户钱包。8080 只携带返回订单地址，不代理渠道密钥和回调。

### 11.6 3001 钱包内部 API

3001 增加仅服务间可调用的通用钱包接口：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/aicp/wallets/{ownerType}/{ownerId}` | 查询可用与冻结余额 |
| POST | `/api/aicp/wallets/precheck` | 校验钱包、余额和权限 |
| POST | `/api/aicp/wallet-transfers/purchase` | 原子扣款、平台费和卖方冻结入账 |
| GET | `/api/aicp/wallet-transfers/by-business-order/{orderNo}` | 按业务订单查单 |
| POST | `/api/aicp/wallet-transfers/{transferNo}/release` | 解冻卖家收入 |
| POST | `/api/aicp/wallet-transfers/{transferNo}/reverse` | 对原交易全部或部分冲正 |
| GET | `/api/aicp/wallet-ledger` | 当前账户资金流水 |

所有变更请求必须携带 `Idempotency-Key`、`X-AICP-Timestamp`、`X-AICP-Service`、`X-AICP-Signature` 和关联 ID。

## 12. 支付与交付编排

### 12.1 正常路径

1. 8080 在本地事务中校验 Listing、创建订单、锁定排他库存并写 Outbox。
2. 用户明确支付后，8080 使用 `trade:purchase:{orderNo}` 作为幂等键调用 3001。
3. 3001 在单一数据库事务中完成钱包分录，返回 `transfer_no=...` 和 `SUCCEEDED`。
4. 8080 将订单置为 `PAID_PENDING_DELIVERY`，在本地事务中创建授权、仓库副本和交付 Outbox。
5. 交付成功后订单进入 `FULFILLED`。

### 12.2 超时与未知结果

- 8080 调用 3001 超时时将订单置为 `PAYMENT_UNKNOWN`，不释放排他库存，也不再次用新键扣款。
- 补偿任务使用业务订单号查询 3001。
- 查到成功则继续交付；查到失败则释放库存并回到可支付或失败状态；持续未知则进入人工异常中心。

### 12.3 扣款成功但交付失败

- 订单进入 `COMPENSATING`，Outbox 重试创建授权和仓库副本。
- 重试必须依赖订单项唯一约束，保证授权和副本幂等。
- 达到配置的重试次数或最大等待时间后，系统调用原转账冲正。
- 冲正成功后订单进入 `REFUNDED`，释放排他库存并通知双方。

### 12.4 免费订单

免费领取仍创建订单、订单项和授权。3001 可以记录金额为零的业务凭证，但不得生成非平衡资金分录。免费订单同样使用唯一约束避免重复领取。

## 13. 充值入口

8080 提供 `/wallet/topup?return_to=<encoded-order-url>` 页面或抽屉：

1. 从 3001 获取支付合规状态、可用支付方式和最低充值金额。
2. 用户选择金额与渠道后调用对应 3001 充值接口。
3. 跳转 3001/渠道收银台完成支付。
4. 渠道回调只进入 3001。
5. 返回 8080 后轮询充值单或钱包余额，显示到账结果。
6. 用户返回原订单，再次确认支付。

`return_to` 只能是 8080 允许列表中的相对路径，防止开放重定向。

## 14. 页面结构

### 14.1 买家端

- 市场首页：真实查询、筛选、URL 同步、分页、加载/空/错状态。
- 剧本详情：公共快照、人物、试读、授权选项、历史普通授权披露。
- 订单确认：购买主体、协议摘要、余额、金额和明确确认动作。
- 充值页：复用 3001 渠道与充值结果。
- 支付结果：处理中、成功、失败、未知和恢复查询。
- 我的购买：订单、授权、协议、仓库入口和申诉入口。

### 14.2 卖家端

- 上架向导：选剧本版本、公共资料、试读、授权、价格和协议。
- 上架管理：草稿、审核中、驳回、在售、保留、已独家成交和下架。
- 销售中心：订单、销量、冻结收入、可用收入、退款冲减。

### 14.3 企业端

- 采购申请：目标 Workspace、理由和授权方案。
- 审批中心：预算、余额、条款、历史授权数和审批记录。
- 企业购买与授权：付款人、订单、企业仓库和授权范围。

### 14.4 平台端

- Listing 审核中心。
- 退款申诉中心。
- 异常订单与补偿任务中心。
- 独家/买断冲突、钱包对账差异和安全告警。

## 15. 权限与安全

建议权限：

| 权限 | 能力 |
|---|---|
| `trade.market.view` | 浏览公开市场 |
| `trade.purchase` | 个人或 Workspace 付款 |
| `trade.purchase.request` | 提交企业采购申请 |
| `trade.purchase.approve` | 审批企业采购 |
| `trade.listing.manage` | 管理当前 Workspace Listing |
| `trade.listing.review` | 平台审核上架 |
| `trade.refund.review` | 平台审核退款 |
| `trade.exception.manage` | 处理异常订单和补偿任务 |

安全要求：

- 用户身份来自认证会话，Workspace 来自可信 `WorkspaceContext`。
- 请求中的 `buyer_id`、`seller_id`、`workspace_id`、价格和平台费不能作为授权依据。
- 8080 与 3001 的内部钱包调用使用独立服务凭据和请求签名，不转发前端伪造的服务头。
- 签名覆盖方法、路径、时间戳、幂等键和请求体哈希；过期请求拒绝。
- 试读 API 只返回审核快照允许的集数，不查询完整私有正文后再由前端裁剪。
- 所有私有订单、授权和仓库查询都必须包含当前用户或 Workspace 条件。
- 支付渠道密钥、钱包服务密钥、完整账户信息不得写入日志。

## 16. 错误处理

统一错误码至少包括：

- `LISTING_NOT_AVAILABLE`
- `LICENSE_OPTION_NOT_AVAILABLE`
- `EXCLUSIVE_LICENSE_RESERVED`
- `EXCLUSIVE_LICENSE_SOLD`
- `ORDER_EXPIRED`
- `ORDER_STATE_CONFLICT`
- `PURCHASE_APPROVAL_REQUIRED`
- `WORKSPACE_WALLET_REQUIRED`
- `INSUFFICIENT_BALANCE`
- `WALLET_SERVICE_UNAVAILABLE`
- `PAYMENT_RESULT_UNKNOWN`
- `DELIVERY_COMPENSATING`
- `REFUND_NOT_ALLOWED`
- `IDEMPOTENCY_CONFLICT`

市场浏览在 3001 不可用时仍可使用。余额、付款、企业审批后的钱包检查、结算和退款必须 fail-closed，并向用户展示可恢复状态，不得伪造成功。

## 17. 对账、监控与告警

### 17.1 日终对账

按业务订单号比较：

- 8080 订单金额、平台费、卖家收入和资金状态。
- 3001 转账金额、分录平衡、冻结/解冻和冲正状态。
- 8080 授权及仓库副本是否存在。

差异进入异常中心，禁止脚本直接改余额或跳过审计修复。

### 17.2 指标

- Listing 审核通过率和平均审核时长。
- 下单、支付、交付和退款转化率。
- 钱包接口成功率、延迟和未知结果数。
- `PAID_PENDING_DELIVERY`、`COMPENSATING` 超时数量。
- 排他库存冲突次数。
- 冻结收入到期未解冻数量。
- 8080/3001 对账差异金额与订单数。

### 17.3 告警

- 资金转账成功但交付超过阈值。
- 同一业务订单出现不同请求哈希。
- 独家/买断存在多份有效授权。
- 钱包借贷分录不平衡。
- 退款冲正金额超过原交易可退余额。
- 3001 钱包服务连续不可用。

## 18. 交付阶段

### 阶段一：交易基础

- 替换前后端 Mock。
- 完成市场、详情、试读、上架审核。
- 建立订单、授权、仓库快照和审计模型。
- 跑通免费领取。

### 阶段二：统一钱包交易

- 3001 建立个人/企业钱包账本和内部接口。
- 8080 接入充值入口、余额和钱包转账。
- 跑通普通、独家、买断的扣款、冻结和交付。
- 完成库存锁、幂等、查单和失败补偿。

### 阶段三：商用治理

- 企业采购审批和企业钱包付款。
- 7 天结算、退款申诉和资金冲正。
- 卖家中心、平台审核中心和异常订单中心。
- 日终对账、业务指标和安全告警。

每个阶段都必须保持可部署、可测试；阶段二未完成前不得对外宣称支持真实付费交易。

## 19. 测试策略

### 19.1 8080 单元与集成测试

- Listing 审核和下架状态转换。
- 四类授权的订单创建与金额快照。
- 独家/买断共享库存的并发条件更新。
- 企业申请、审批和付款权限矩阵。
- 扣款成功后的授权及仓库副本幂等创建。
- 退款资格、库存恢复和授权撤销。
- Outbox 重试、查单、补偿和自动退款。

### 19.2 3001 钱包测试

- 个人/企业/平台钱包唯一性。
- 购买转账的复式分录平衡。
- 幂等重试返回同一结果。
- 相同幂等键、不同请求返回冲突。
- 并发扣款不透支。
- 冻结收入解冻只执行一次。
- 全额和部分冲正不超过原交易金额。
- 充值入账正确投影到钱包。

### 19.3 契约测试

- 8080 与 3001 请求/响应字段、金额单位和状态枚举一致。
- 服务签名、时间窗口和请求哈希一致。
- 超时、5xx、重复请求和未知结果行为固定。

### 19.4 端到端测试

必须覆盖：

1. 免费领取并进入个人仓库。
2. 普通授权充值、付款、交付和卖家冻结入账。
3. 两个买家并发购买独家授权，只有一笔成功。
4. 买断成交后所有新授权停售，历史普通授权仍有效。
5. 企业申请、审批、企业钱包付款和企业仓库入库。
6. 3001 扣款成功后 8080 宕机，恢复后自动完成交付。
7. 钱包调用超时后按原订单查单，不重复扣款。
8. 交付持续失败后自动冲正并恢复排他库存。
9. 已交付订单申诉退款、审核、冲正、授权撤销。
10. 7 天到期后卖家收入只解冻一次。

## 20. 验收标准

- 市场页面不再依赖硬编码数据或 Mock 成功响应。
- 上架审核通过前，剧本不会进入公开市场。
- 免费、普通、独家和买断都能形成订单、授权、仓库副本和审计记录。
- 并发购买独家/买断时最多一笔订单完成支付和授权。
- 任意 API、消息或任务重试不会重复扣款、入库、结算或退款。
- 3001 不可用时市场浏览正常，资金操作明确失败或保持可恢复未知状态。
- 个人订单只能使用个人钱包；企业订单只能使用目标 Workspace 钱包。
- 扣款成功但 8080 中断后，订单能自动恢复交付或自动退款。
- 退款严格冲正原交易，独家/买断仅在退款成功后恢复库存。
- 买家只能读取购买时授权版本，不能访问卖家后续私有版本。
- 8080 与 3001 可按业务订单号完成资金、订单、授权三方对账。

设计确认 3C/4：数据库字段、索引与迁移

关键修正：项目中已经存在 workspace_assets + asset_versions 市场资产模型。新方案不再继续扩建 platform_assets 形成第三套资产库，而是将生成资产迁入 Workspace 资产模型，最终退役 platform_assets。

一、资产模型收敛

现状：两套资产本体
platform_assets：生成历史
workspace_assets：资产市场/Workspace 库
归属、收藏、发布和字段口径重复
→
目标：一套资产本体
workspace_assets：可变元数据与归属
asset_versions：不可变文件版本
generation_tasks：生成过程
市场发布直接复用现有模型

platform_assets 在迁移期只承担旧接口兼容，不再作为新页面的数据源。这样“生成成功 → 资产管理 → 团队共享 → 市场发布”使用同一个 asset_uuid。

四、generation_tasks：任务归属与重试链

新增 workspace_id VARCHAR(64) NOT NULL、created_by BIGINT NOT NULL、content_project_id BIGINT NULL、asset_type VARCHAR(32) NOT NULL DEFAULT 'OTHER'、retry_of_task_id BIGINT NULL、idempotency_key VARCHAR(64) NULL、request_id VARCHAR(64) NULL。保留现有 project_id 作为 source_canvas_project_id 兼容字段，后续单独重命名，不在本期破坏已有 Mapper。

成功约束：status=SUCCEEDED 时必须存在至少一个关联 asset_version；若资产入库失败，任务保持 RUNNING/补偿中或转 FAILED，不允许先标成功再留空资产。

七、迁移步骤与数据回填

  1. 一致性修复：先统一 Workspace ID 来源。使用账户中心返回的真实 ID；开发环境个人默认统一为 personal_{userId}。禁止继续使用 schema 中的 personal:/ent: 字符串拼接。
  2. 加法迁移：为 workspace_assets、asset_versions、generation_tasks 增加 nullable 字段和新表/索引；H2/MySQL 同步提交。
  3. 回填：逐批把 platform_assets 转为 workspace_assets + asset_versions，保留原 uuid，写 legacy_platform_asset_id；项目通过 canvas_projects.content_project_id 映射，无法映射进入未归档。
  4. 分类映射：优先读取明确 category；否则按 generation_tasks.sub_type 映射；仍无法识别设 OTHER 并记录迁移告警，不静默猜测。
  5. 收藏迁移：platform_assets.favorite=1 转为创建者的 workspace_asset_favorites；市场 asset_favorites 不改，因为它收藏的是 listing。
  6. 双写：GenerationExecutor 在特性开关下写新 canonical 模型并继续写 platform_assets；对 asset_uuid、数量、Workspace、项目、文件引用做影子校验。
  7. 切读：新工作台只读 canonical 模型；旧接口继续读 platform_assets。双写稳定且历史回填核对通过后停止旧写。
  8. 退役：旧接口调用量连续 14 天为 0 且至少经过 60 天兼容期后，备份并删除 platform_assets Mapper/实体/表；先删代码，下一发布再删表。

八、迁移验收与回滚

验收：总资产数、按 Workspace/项目/分类计数、文件引用可用率、成功任务关联资产率、收藏数、孤儿记录数必须输出核对报告；成功任务无资产率必须为 0。
回滚：迁移期间不删除旧列/旧表；读开关可切回旧查询，双写失败进入补偿队列。已写入 canonical 的数据保留，不做反向破坏性回滚。

7. 二次审查：V7 仍有 8 个需要关闭的问题

级别问题为什么仍有风险建议处理
阻塞 M0技术附件尚未生成PRD 有字段和示例，但没有可校验的 OpenAPI、JSON Schema、完整 ERD 和事件契约。M0 计划第一批任务先冻结这四类文件，再写业务代码。
阻塞 M0迁移回滚存在读路径缺口“新写只进新模型”与“回滚后旧 API 读旧表”同时成立时，新项目在回滚后不可见。明确兼容投影/双写或回滚期旧 API 读取新模型适配层，并补迁移演练用例。
阻塞 M0项目状态聚合规则未定义项目、内容单元、版本都有状态，但项目卡片的内容状态如何计算不明确。定义项目状态为派生视图，列出单元状态→项目状态的优先级与刷新事件。
M0 补齐事件投递语义缺失已列事件名，但没有 at-least-once、Outbox、顺序键和消费幂等规则。事件目录中补生产事务、去重键、重试和死信策略。
M0 补齐稳定键命名可能误导`EP{n}` 作为 stable_key 与“拖拽排序后 ID 不变”容易冲突。稳定键使用 UUID/短 ID，`display_no` 单独表达第几集/章。
M1 补齐异常与空状态仍缺页面级定义PRD 定义了错误行为，但尚无解析失败、无权限、版本冲突、部分成功、离线恢复的完整交互稿。为 M1 纵向切片输出正常/空/加载/失败/冲突/无权限六态原型。
M1 补齐部分成功状态不够细`partial_completed` 没定义成功子项、失败子项、取消后续和费用展示结构。增加 batch_job_items 与按子项重试、取消、结算合同。
评审补齐指标多数只有“持续提升”无法作为灰度转全量的退出门槛。试点两周建立基线后，在灰度方案中冻结目标值、护栏指标和回滚阈值。
最终判断：V7 已经不是概念方案，而是可用于拆解 M0/M1 的开发基线。当前最合理的下一步不是继续增加功能，而是先关闭“技术附件、迁移读路径、项目状态聚合”三个阻塞项，再形成 M0/M1 实施计划。

任务监控中心：三种架构路径

目标：统一生成任务与交易任务，并支持用户操作、运营处置、告警、SLA 和对账。

生成服务　交易服务　钱包服务
↓ 标准事件 / Outbox ↓
统一任务投影 + 操作编排 + 告警/SLA
↓
用户任务中心　｜　运营控制台

A. 统一任务事件中心（推荐）

保留各业务状态机，通过统一事件、时间线和读模型聚合；操作仍回到所属业务服务执行。

优点：边界清楚，可追溯，适合分阶段融合 B 与 C。
代价：需要事件规范、投影表和补偿机制。

前端任务中心
生成 API
订单 API
钱包 API

B. 前端聚合现有接口

页面分别请求生成、订单和钱包接口，在浏览器中拼装状态和时间线。

优点：交付快、后端改动少。
代价：分页、权限、对账和跨服务状态一致性难以可靠实现。

统一流程编排引擎
控制所有状态迁移
生成执行器
交易执行器
财务执行器

C. 全量流程编排平台

把生成、交易、结算和补偿全部迁入统一工作流引擎，由中心直接控制状态。

优点：控制力最强。
代价：改造面过大，会重写现有业务边界，不适合作为当前完善项目。

推荐落地方式

采用 A，并分两层交付：先完成统一可视、操作闭环与异常队列；同一模型上继续补充 SLA、告警、自动对账和人工工单。不是先做一个一次性只读页面，再推倒重来。
